## Что уже сделано правильно и **не нужно ухудшать**

- Отдельный `PROJECT.md` не заменён универсальной инструкцией; его отсутствие блокирует реализацию.
- A1–A4 не являются координаторами по умолчанию; A5 не уполномочен автоматически на релиз, расходы и чужие модули.
- `COMMON.md` §4 прямо признаёт, что GitHub label **не** атомарный lock.
- Необходимы actual SHA, PASS/FAIL/NOT_RUN и независимое ревью; запрет ложных «DONE» верен.
- `COMMON.md` §6 не создаёт искусственный G0, если проект его не требует.
- Сохранено недоверие к инструкции из внешних данных и запрещено открывать секреты.

## Дополнительная рекомендация к роли A1–A4

Согласен с альтернативной моделью из `2026-11-05-role-model.md`: A1–A4 в универсальном ядре — равноправные слоты разработчиков; frontend/backend/data/core являются **опциональными профилями проекта**, не фиксированным назначением. При этом нельзя игнорировать обязанность каждому разработчику владеть проверяемым deliverable, границей файлов и реальным контрактом. `A5` отвечает за координацию, но не превращается автоматически в владельца всех интеграционных доменных данных.

## Ограничения фактов

- PR и Issues на исходном чтении отсутствовали; их отсутствие само по себе не нарушение для новой библиотеки шаблонов. Требуется процесс, когда она станет использоваться.
- Endpoint API Actions не удалось прочитать через доступный коннектор; отсутствие CI установлено **по полному Git-дереву**, а не по результатам Actions.
- Последний исходный commit помечен GitHub как unsigned; подпись сама по себе не защищает от плохих изменений.
- Этот файл не утверждает, что найден конкретный data leak, гонка агентов или сломанный выпуск. Все перечисленные последствия — риски, требующие теста.

## Главный критерий успешности следующей версии

Для произвольного проекта и набора из пяти агентов должно быть возможно **до первого изменения** ответить по документам и GitHub: кто имеет права, какой task/lease у каждого, какой commit и scope зафиксирован, кто владеет публичным контрактом, как проверить результат, кто разрешает merge/release и как остановиться при конфликте. Ответ должен быть подтверждаемым, а не основываться только на заявлениях агента.
