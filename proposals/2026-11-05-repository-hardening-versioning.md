# Предложение: GitHub hardening, проверка промптов, происхождение и выпуск

**Статус: draft; предлагается, но НЕ реализовано.** Дополняет [операционный аудит](2026-11-05-deep-operational-audit.md). Закладывает технические гарантии вместо исключительно текстовых обещаний.

## 1. Защитить основную ветку (P1)

Факт baseline: у `main` `protected=false`; GitHub API указывает `protection.enabled=false`. В `COMMON.md` §4 текст запрещает прямой commit лишь в *защищённую* базовую ветку. Предложить исправление:

> «Во всех проектах запрещены прямые изменения базовой ветки независимо от того, включена ли техническая защита. Любое изменение идёт в отдельной ветке и PR. Исключения допустимы только через документированное аварийное разрешение с независимой проверкой и журналом».

Конфигурация после согласования: PR required (не менее одного независимого reviewer; для A5-PR — не сам A5), required status checks с актуальным SHA, запрет force push/deletion, review stale approvals после существенного diff, CODEOWNERS или проектный эквивалент. Если возможности GitHub/тарифа не обеспечивают режим, **не объявлять защиту технически обеспеченной**; указать это в рисках и использовать handoff/режим ограниченного доступа. Перед изменением branch protection проверить права и фактическую конфигурацию. Для уже существующих проектов не применять настройки без решения владельца.

## 2. Система тестов для промптов (P1)

Предложить файлы (пока их **нет** в baseline):

- `.github/workflows/prompt-checks.yml` — при PR запускать только проверку Markdown, ссылок, структуры и тестов сценариев.
- `tools/check_prompt_repository.py` — проверка обязательных файлов, валидных относительных ссылок, отсутствия ссылок на несуществующие role-ID, дублирующихся версий и невыполненных плейсхолдеров в *принятых* шаблонах. `PROJECT.template.md` намеренно содержит placeholder и не должен проваливать сборку без режима deployment.
- `tests/prompt_scenarios/` — структурированные входы и ожидаемые ограничения из [сценарной матрицы](2026-11-05-prompt-scenario-regressions.md).
- `tests/fixtures/` — синтетические проекты: API-only, Godot-like UI, data pipeline, docs/research, single-developer и пять параллельных агентов.

Примеры lint-инвариантов:

1. В `README.md` ссылки на `prompts/COMMON.md`, A1–A5 и `PROJECT.template.md` существуют.
2. Каждый индивидуальный A*.md содержит ссылку на COMMON и требует утверждённый PROJECT.md.
3. Во всех шаблонах A1–A4 роль **разработчик**; A5 — **главный**, но не получает автоматических прав на релиз/расходы/доступ к чужим файлам.
4. Нельзя заменить `NOT_RUN` на PASS для неподтверждённой команды.
5. Изменение role-template сопровождается обновлением версии, changelog и прохождением сценарных regression tests.
6. `PROJECT.template.md` валиден как *неутверждённый шаблон*, но `PROJECT.md` в целевом проекте блокируется, если `status != APPROVED` для операций, требующих approval.
7. Переход в DONE требует ссылку на result SHA, релевантные checks и reviewer-policy.

Важно: линтер может поймать структурные нарушения, но не гарантирует послушание агента тексту. Сценарные LLM-тесты нужно выполнять отдельно на поддерживаемой модели/конфигурации и оценивать по наблюдаемым действиям; не полагаться на самоотчёт.

## 3. Versioning и защита от дрейфа (P1)

Ввести `VERSION`, `CHANGELOG.md`, `sources/SOURCE-MANIFEST.md` и `docs/COMPATIBILITY.md` после утверждения. Предлагаемое правило:

- **MAJOR**: изменены права, утверждение, роли/границы, статус DONE, безопасность или протокол задач.
- **MINOR**: добавлены обратносуместимые профили, формы, проверки и необязательные практики.
- **PATCH**: редактура без изменения нормативного смысла. Проверять классификацию ревьюером.

Проект должен ссылаться на **immutable commit SHA** универсального архива и точную версию `COMMON.md` / role prompts в `prompts.lock`. При обновлении: список изменённых правил, оценка совместимости, новые тесты, approval проекта, rollback на старый SHA. Не использовать плавающую ссылку на `main` как единственную версию для действующих агентов.

Предлагаемый `prompts.lock`:

```yaml
archive_repo: AndreyCokol/General-Archive
archive_commit: "<full-40-char-commit-sha>"
archive_version: "1.x.y"
project_approval: "<decision-link>"
roles: [A1, A2, A3, A4, A5]
```

Значения в примере — placeholder, не реальный lock.

## 4. Исходные протоколы и provenance (P1)

Текущий README указывает происхождение из пользовательского протокола и My_shelter. Для строгой истории добавить записи **отдельно** для:
- ChemSim: `openspec/agents/prompts/mandatory-work-protocol-a1-a5.md`, commit + hash содержимого + ссылка + описание отличий;
- My_shelter: `docs/book-01/agents/prompts/COMMON.md`, SHA `87c1303373aae796f714938342d699fd09c0a2a2` и ссылка + описание отличий;
- General-Archive: universal `prompts/COMMON.md` baseline `0c890668cedb884ff8ae441bffe26755aea99c21`.

Сохранить неизменяемые snapshots оригиналов **только если это разрешено правами и не раскрывает данные**; иначе сохранить SHA, location и точную матрицу переносов без копирования. Не заявлять «точно перенесён» до сравнения file hashes и сохранения diff.

## 5. Privacy, безопасность и destructive operations (P1/P2)

В `PROJECT.md` явно перечислить: внешние системы, допустимые среды и тестовые аккаунты, запрещённые API, класс данных, допустимые публикации, ресурсные расходы и permission scope. Для destructive action (удаление, стирание history, изменение секретов/доступов, запись в production, deploy/publish) — отдельное явное подтверждение, принцип наименьших прав, безопасный dry-run когда возможен, журнал результата. Если требуется откат — сначала удостовериться, что он не уничтожит новые данные.

Отчёты агентов не должны содержать токенов, ключей, клиентских данных и содержимого приватных подключений. Публичность архива = решение владельца; найденное состояние репозитория `public` не означает, что любые будущие материалы могут быть публичными. Для расширения внешнего использования обсудить `LICENSE`, `SECURITY.md` и сканирование секретов.

## 6. Поставка и критерии приёмки

Считать пакет готовым, когда:
- `main` реально защищена **или** риск/ограничение явно зафиксированы владельцем для текущего режима;
- чистый PR прогоняет линтер и проверку ссылок; сломанная ссылка или роль проваливают checks;
- vNext имеет changelog, однозначный immutable source и миграцию;
- в тестовом проекте нельзя перевести DRAFT project в работу по коду без решения;
- независимый reviewer и required checks подтверждены ссылками; при их отсутствии честное `BLOCKED/NEEDS_REVIEW`.
